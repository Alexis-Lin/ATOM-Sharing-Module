01 · 结论先行

三条判断

这三条决定了后面所有结构。如果不认同其中任何一条，后面的方案要重来。

判断 A

落到电商，归因就不再靠猜

跳应用商店的链路里，iOS 没有官方的按人延迟深链、微信屏蔽 itms-apps、国内安卓没有统一商店与 Install Referrer——只能做概率匹配。改成落到购买页后，归因点从"安装时刻"移到"下单时刻"：订单一定有号、一定能带码、一定进账本。整条阶梯每一层都是确定性的，没有概率层。

判断 B

落地页是唯一的变化点

分享物（图片、短链）在全球是同一份；地区差异、环境差异、目标差异全部由 H5 落地页在运行时吸收。这意味着 App 端和 Atom 设备端不需要写任何地区逻辑——它们只负责渲染一个 token。国际化不是多做几套分享 UI，是多配几份 Profile。

判断 C

一个码，两个时刻

优惠码在结算时是折扣（促成交，被邀请人的钩子），在首次激活 Atom 时是凭证（做归因，邀请人的奖励依据）。同一个码复用两次，所以即使在天猫/京东这类归因黑洞里成交，激活那一刻也能把关系补回来。这是电商链路能兜底的根本原因。

每种组合都有三条道：主路（我们希望走的，归因最干净）、备路（用户偏要去第三方电商时走的）、兜底（前两条都失败时的最后一次机会）。注意兜底那条在所有组合里是同一条——这就是它作为架构底座的价值。

03 · 归因阶梯

五层，越往下越兜底，全部确定性

按顺序命中即停。确定 = 系统自动、无需用户动作；需动作 = 依赖用户填/用了那个码；平台口径 = 数据由第三方平台回传，我们无法自证。

层归因点触发时机确定性覆盖范围与说明

L4 App 内自助补填 激活后 7 天内 需动作 "忘填邀请码？"入口，限时限次。同时给邀请人一个"提醒 TA 填码"的动作，把补录的压力转移到有动机的一方。

已决策的简化口径：P0 只做 L0（订单带 token）与 L3（激活填码）+ L4 补填；L1/L2 不做；不记录点击。因为 L3 覆盖全渠道且 100% 确定，我们不必强求 L0 的漏斗完美。L0/L1 优化的是"成交转化"，L3 优化的是"关系记账"。两件事分开算 KPI，不要混。

落地页必须做的六件事

  • 认人：token → 邀请人昵称/头像/训练数据，做社交证明。人比产品更有说服力。
  • 认环境：UA 判微信内 / 系统浏览器 / 桌面，决定 CTA 形态与是否可唤起小程序。
  • 认地区：加载对应 Profile（见 §06）。用 App Store 区/店铺归属判定，不要用 IP——出差和 VPN 会把判定打歪。

  • 始终显示明文码：链路里任何一跳断了，用户手上还有这个码。
  • 富媒体卡片：配 OG / 微信 JS-SDK 的标题、描述、缩略图，让链接在聊天里渲染成卡片而不是裸网址。这不是第三种形式，是同一个 URL 的渠道渲染。

05 · Token 与链接结构

一人一码，永久不变

结构

短链　https://bp.fit/i/7K2A?s=post&c=wx
明文码　ALEX-7K2A
二维码　编码同一条短链
  • 7K2A = 邀请人 token，永久绑定，是唯一被解析的部分。Base32 去歧义字母表（无 0/O/1/I/L），4–6 位起步。
  • ALEX- 前缀纯装饰，便于人念人记，服务端只取后缀。改昵称不影响归因。
  • s 场景（哪个分享入口生成的）、c 渠道，仅用于分析，永不参与归因。

为什么参数必须可丢

  • 图片会被截图转发、二维码会被翻拍、短链会被手抄。任何依赖参数完整性的设计在这三种动作面前都会碎。
  • 把归因押在 token 上、把分析押在参数上，意味着一张图被转发十手之后归因依然正确，只是渠道标签失真。这是可接受的失真。
  • 推论：不做一次性链接、不做有效期链接（活动券除外）。邀请关系是长期资产。

07 · 奖励与风控

两侧各两样，全部可叠加 已决策 09-03

主机 $239–299（≈ ¥1,700–2,150）。每一侧都是「一笔小钱 + 一个月 PRO」：钱让人填码，PRO 是全球都能无条件发的底座。永远不给现金。

力度判断

  • 好友侧 ¥50 / $10 占客单价 3–4%：够让人填码，不是购买理由。落地页 hero 讲的是"优惠已自动生效"，不是折扣力度。
  • 每成功推荐一台总成本约 $20 真实 / $25 名义，占客单价 8% 左右；整包控制在 10–12% 内。
  • 同一个 $10，在好友侧是象征，在邀请人侧是一件配件的 1/6 到 2/3——这是持续邀请的真实动力。

结算时点

  • 好友的 PRO 在激活填码那一刻发（它本身就是填码的激励）。
  • 邀请人的奖励在好友确认收货 + 完成激活之后发——硬件退货率不为零。
  • 账本：attributed → qualified → settled，退货 reversed。

反薅与用词

  • 邀请人奖励只在购买 + 激活后触发，注册不触发——假号无利可图。
  • 同设备指纹 / 同支付账号 / 同收货地址高频 → 人工审核；异常速率挂起而非拒绝；邀请人需有真实训练记录。
  • 叫「抵扣金」不叫「现金」：只能店内用、有有效期，避开个税与资质，不在账上堆成无期限负债。
08 · 接入现有架构

不是新模块，是分享模块上的一层薄挂载

邀请是内容的副产品，不是内容本身。所以它不新增载体族、不新增自由度层级，只在既有五层模型里各加一点点。

09 · 待拍板

六个需要在会上定的问题

电商 / 运营

小程序商城这一路走不走得通？

国内方案的强弱几乎全押在这里。能上小程序商城 = L0 直通、归因近 100%、传播衰减最小；上不了则国内退化为"优惠码 + 激活回填"双腿走路，仍可用但转化会打折。

运营 / 法务

天猫/京东能不能挂自定义优惠码？

决定 L1 是否成立。平台对自定义券码有规则限制，需与店铺运营确认可用形态（专属券/口令/店铺优惠码），以及能否回传核销明细。

硬件 / App

邀请码填写放在激活流程的哪一步？

L3 是全渠道兜底层，它的转化率直接决定整个方案的归因覆盖率。建议放在配网成功后、首次训练前，可跳过但有一次明显提示。

PM

P0 只做"内容图挂载"，还是连专用邀请卡一起做？

挂载几乎零成本（G1 改造），量最大；专用卡要新模板 + 落地页 + 设备端。建议 P0 只做挂载 + 落地页，专用卡放 P1。

增长

邀请人奖励给什么、给多少？

硬件客单价高，奖励力度需要财务口径。先定形态（权益 vs 现金）再定数值——形态定了才能开始做 UI。

硬件

设备屏能不能显示动态二维码？

决定设备端邀请是"每台设备固定一张图"还是"按登录用户生成"。若设备只能显示静态图，则设备端邀请无法归因到具体用户，需降级为渠道码。
