## 0. 一句话定位

> **一套分享模块，覆盖全 App 全场景。**
> 不同入口在分享时，只是**调用不同的内容原子 + UI 模板 + 载体**，代码与功能只维护一套。

**北极星指标：流量 · 传播 · 留存**（会议共识：分享的本质就是为了这三件事）。所有设计规则都回归到这三个字。

## 1. 核心抽象：五层解耦模型

会议最重要的洞察——"**排列组合是无穷的，但底层原子模块是有限的**"，以及说话人 1 反复强调的"**解耦**"。据此把分享拆成 5 个正交、可独立替换的层：

```
① 分享主体 Subject   —— 我在分享"什么"？（某次训练 / 某个动作 / 某周打卡 / 某个成就…）
        │
② 内容原子 Atom      —— 用哪些"积木"来表达？（总结数据 / 动作列表 / 肌肉热力图 / 火柴人…）
        │
③ 组装模板 Assembly  —— 积木怎么"排"？（默认模板 + 菜单式勾选 + 短图/长图/卡片）
        │
④ 载体格式 Carrier   —— 以什么"形式"输出？（图像 / 视频 / H5交互 / 数据MD·CSV·JSON / PDF报告）
        │
⑤ 分发链路 Path      —— 怎么"送达"对方？（送达人：社交/扫码/公域H5；送达机器：喂给 Agent）
```

**为什么要这样分层：**
- 层与层之间解耦后，"分享一张图 / 存本地 / 甩个链接 / 扫码"只是**第 ④⑤ 层的不同选择**，不改变前三层。
- 新增一个分享场景（如单动作分享），只需在第 ①② 层配置"主体→原子映射"，无需重写分发逻辑。
- UI 个性化的自由发挥空间集中在第 ③ 层，框架（①②④⑤）保持稳定——正如会议共识："框架别歪了，风格越往后越自由。"

## 2. 第①层 · 分享体模型：什么可以被分享（What）

### 2.1 关键区分：内容 vs 实例 ✅ 已决策 2026-07-16

同样是"分享一节课"，其实是**两个不同的分享体**，目的完全不同：

| | 分享课程内容（内容态） | 分享训练结果（实例态） |
|---|---|---|
| 潜台词 | "这节课很好，推荐给你" | "这节课**被我练过之后**的结果" |
| 展示什么 | 课程的模板与内容（官方数据） | 做了几个动作、卡路里、次数、容量（用户数据） |
| 数据来源 | 官方内容库 | 用户 × 内容 的关系数据 |
| 价值 | 引流（链公域 H5） | 成就感、传播动力最强 |

> 推广开来：**任何官方内容都有机会叠加"用户 × 内容"的关系**。分享体 = 内容实体 × 用户关系态。

### 2.2 两轴模型：内容实体 × 用户关系态

**轴一 · 内容实体（锚定"关于什么"）**
- `E1` 动作（动作库）
- `E2` 课程（workout / oneset / challenge）
- `E3` 计划 / 挑战活动（未来）
- `E4` 教练 / 老师（真人教练、未来 AI 教练）——**人也是内容实体**
- `E5` 肌肉 / 部位（肌肉字典里的肌群，如肱二头肌）
- `E6` 器械（哑铃、杠铃、绳索……）
- `E7` 动作模式 Pattern（上肢推 / 上肢拉 / 蹲 / 髋铰链 / 弓步 / 旋转 / 核心……）——专业训练视角的分类
- `E0` 全局——不锚定具体内容，锚定"我这个人"
- `E12` **推荐邀请**（Referral）🆕 2026-09-03——只有 `R1`（我的邀请）这一态；规模很小的一个实体，只为让邀请卡在矩阵里有位置，详见 §14

> **实体轴是开放的**，且分两类：**对象实体**（E1~E4：动作、课程、计划、教练——具体的"东西/人"）与**分类实体**（E5~E7：肌肉、器械、模式——给动作打标签的维度）。分类实体的 R2 天然是"**平衡/覆盖**"类叙事（推拉比、肌群覆盖热度、器械偏好），这正是原子化组合产品的独有优势——普通课程 App 拿不出"我和肱二头肌的历史"、"我的推拉平衡"。E7 也是 C4 里 PPS 六边形、体适能雷达这些衍生指标的数据地基。

**轴二 · 用户关系态（锚定"我和它的关系"）**
- `R0` **内容态**：官方模板本身，无用户数据——"这个好"
- `R1` **实例态**：我练完**一次**的结果——"我练了，练成这样"
- `R2` **聚合态**：跨时间的累计与趋势——"我坚持、我成长"
- `R3` **衍生态**：系统对我数据的评价（评级/勋章/雷达）——"我达成了"

### 2.3 分享体矩阵（可被分享的全集）

| 实体 ＼ 关系态 | R0 内容态 | R1 实例态（单次） | R2 聚合态（历史） | R3 衍生态（评价） |
|---|---|---|---|---|
| **E1 动作** | 动作卡（类武将卡，链公域动作库） | 单动作训练结果：次数/重量/火柴人/AI 点评 | 该动作历史记录、PB 曲线 | 动作达成徽章、动作评分 |
| **E2 课程** | 课程卡（链公域课程库） | **课后报告**（P0） | 该课 N 刷、成绩趋势 | 课程评级 A/B/S/SS |
| **E3 计划/挑战** | 计划简介卡 | 某次挑战完成 | 计划完成进度 | 挑战达成勋章 |
| **E4 教练/老师** | 教练介绍卡（链公域教练主页） | 跟某教练练的单次记录 | **我 × 教练的关系**：累计跟练 N 节、时长、进步 | 师徒里程碑徽章（如跟练 100 节） |
| **E5 肌肉/部位** | 肌肉科普卡（解剖、相关动作，链肌肉字典） | 本次练到该肌群的强度 | **我 × 肌肉的历史**：练过 N 个动作、N 次训练、总容量 | 部位专精徽章（如"背部大师"） |
| **E6 器械** | 器械介绍卡（用法、适配动作） | 本次用它练的记录 | **我 × 器械的关系**：最爱的哑铃，用过 N 次、练过哪些动作 | 器械里程碑（如"杠铃 10 吨俱乐部"） |
| **E7 动作模式** | 模式科普卡（定义 + 代表动作） | 本次的模式分布（"今天全是推"） | **我的模式平衡**：推拉比、各模式容量占比、欠练模式 | 模式均衡评级、PPS 六边形徽章 |
| **E0 全局（我）** | **个人主页**（未来：头像、照片/视频集、成就墙） | 单次自由训练 | **周期打卡**（周/月/年、streak） | 体适能雷达、勋章墙、PB 集 |

- **高光影像 / 火柴人动态**：不是独立实体，而是依附于任意 `R1` 实例的**媒体资产**，可从实例中切出来单独分享。
- **数据导出（给 Agent）**：不是矩阵中的格子，而是把任意格子的数据换一种载体（Markdown/CSV/JSON）输出——属于第④层的**数据载体族**（见 7.2/7.3），Pro 功能。
- 分享动力梯度：`R1 > R3 ≈ R2 > R0`（实例最有动力，内容态动力弱但引流价值最高）。

### 2.4 分享源 → 分享体 绑定（更新版）✅ 已决策 2026-07-16

用户**从哪里发起分享，就分享什么**——分享体由发起位置隐式决定，用户无需先"选择分享什么"。当一个分享源同时命中两个关系态（如动作详情页里既有官方内容又有我的历史），默认取用户数据态，提供轻量切换：

| 分享源（App 内发起位置) | 绑定分享体（矩阵格子） | 默认核心原子 |
|---|---|---|
| (a) 动作库 · 某动作详情页 | E1·R0 动作卡；若有训练历史可切 E1·R2 | 动作卡 + 肌肉热力图(解剖态) |
| (b) 某节课页面 | E2·R0 课程卡；练过可切 E2·R1/R2 | 课程卡 |
| (c) 课后报告 / 某节课训练记录 | E2·R1 课后报告 | 总结数据 + 热力图 + 动作列表 |
| (d) 影像记录 / 高光火柴人动态 | 依附 R1 的媒体资产 | AI 火柴人 + 高光视频 |
| (e) 周期统计页（周/月/年） | E0·R2 周期打卡 | 周期统计 + 历史对比 |
| (f) 成就 / PB / 雷达页 | E0·R3 成就 | 外化成就标识 / 雷达图 |
| (g) 已训练动作 · 历史记录页 | E1·R2 动作历史 | 历史曲线 + PB |
| (h) 教练主页 / 课程页教练区 | E4·R0 教练卡；有跟练史可切 E4·R2 | 教练卡 + 师徒关系数据 |
| (i) 个人主页（未来） | E0·R0 个人主页 | 名片 + 成就墙 + 照片/视频集 |
| (j) 肌肉字典 / 肌群详情页 | E5·R0 肌肉卡；有训练史可切 E5·R2 | 肌肉卡 + 热力图(解剖态) + 历史 |
| (k) 器械详情页 | E6·R0 器械卡；用过可切 E6·R2 | 器械卡 + 使用历史 |
| (l) 模式统计 / 体适能报告视图 | E7·R2 模式平衡 | 模式卡（PPS 六边形/推拉比） |
| (m) 单动作完成 / 动作报告 | E1·R1 动作级报告 | 火柴人 + AI 点评 + 洞察卡 + PB |
| (n) 计划完成页 | E3·R2 计划级报告 | 阶段对比 + 洞察卡 + 坚持度 |
| (o) 训练中/训练后 · 影像页 | M 类媒体资产 | 高光视频 M2 / 高光照片 M3 / 姿态叠加 M5 |
| (p) 影像风格化入口 | M4 漫画/风格化影像 | 风格模板选择 + 数据角标 |

> 注：火柴人既是"课后报告"里的可选**原子**，也因入口 (d) 可作为媒体资产单独分享——同一积木，两种调用，正是原子化架构的意义。

### 2.5 分享体优先级（矩阵格子视角）

| 分享体（格子） | 说明 | 当前状态 | 分享意愿 | 优先级 |
|---|---|---|---|---|
| **E2·R1 课后报告** | 练完一节课/一次 workout 的结果 | ✅ 已有（较简陋） | 高（动态、每次不同、最像健身房打卡） | **P0** |
| **E0·R2 周期打卡** | 7天 / 本月 / 今年累计的统计概览 | ❌ 缺 | 高 | **P1** |
| **E1·R1 动作级报告** ★ | 单动作完成后的质量报告：火柴人 + AI 点评 + 洞察 | ❌ 缺 | 高（即时反馈、独有） | **P1** |
| **E3·R2 计划级报告** ★ | 4/8 周计划完成：起点 vs 终点、能力变化 | ❌ 缺（依赖计划功能） | 极高（成长叙事最强） | **P1** |
| **E1·R2 单动作历史** | 某动作历史记录/PB 曲线 | ❌ 缺 | 中 | **P1** |
| **E0·R3 成就 / 里程碑** | PB、勋章、评级(A/B/S/SS)、雷达升级 | ❌ 缺（依赖功能补全） | 高（游戏化、炫耀） | **P1 占位** |
| **M 类媒体资产（高光视频/照片）** ★ | AI 自动选材的高光片段与静帧 | 🟡 部分 | **高**（平台原生内容） | **P1** |
| **M4 漫画 / 风格化影像** ★ | 训练影像 AI 风格化——最强传播形态、降低出镜门槛 | ❌ 缺 | **最高** | **P1 · 建议单独立项** |
| **E1/E2·R0 官方内容卡** | 动作卡/课程卡，落公域 H5 | ❌ 缺 | 低（非个人产出，动力弱、引流价值高） | **P2** |
| **E4·R0/R2 教练卡与师徒关系** | 教练介绍 + 我跟练 N 节/时长（会议判断"分享老师国内肯定会有"） | ❌ 缺 | 中（关系叙事有情感动力） | **P2** |
| **E5·R2 我 × 肌肉的历史** | 肱二头肌：练过 N 动作、N 次训练、总容量 | ❌ 缺（数据已有，视图缺） | 中（专业感、独有） | **P2** |
| **E6·R2 我 × 器械的关系** | 最爱的哑铃：用过 N 次、练过什么动作 | ❌ 缺（依赖器械维度数据） | 中（趣味叙事、独有） | **P2** |
| **E7·R2 我的模式平衡** | 推拉比、各模式容量占比（动作→模式映射可现场算） | ❌ 缺（数据可算，视图缺） | 中（专业用户高意愿、独有） | **P2** |
| **数据导出（给 AI / Agent）** | 任意格子数据的 Markdown/CSV 载体变体 | ❌ 缺 | 极客高意愿 | **P2 / Pro** |
| **E0·R0 个人主页** | 名片、照片/视频集、成就墙 | ❌ 缺（依赖社区/主页功能） | 中 | **P3 / 未来占位** |
| **E8~E11 健康域（体重/饮食/跑步/睡眠）** | 大一统健康数据中心的分享预留（见 2.8） | ❌ 缺（依赖数据域接入） | 高（大众健康叙事） | **P3 / 预留占位** |

> 会议共识：**R1 实例态分享动力最强**（"我每次练都不一样，能体现成就感"），R0 内容态动力最弱（"平台固定通用的东西，没太多动力"）但引流价值最高。→ 先做课后报告，再补单动作/周期/官方。

### 2.6 报告作为跨粒度的分享体族 ✅ 新增 2026-07-18 ★

**课后训练报告不是一个格子，而是一族**——同样叫"报告"，在不同粒度上是不同的分享体，内容侧重完全不同：

| 粒度 | 分享体格子 | 触发时机 | 报告内容侧重 | 优先级 |
|---|---|---|---|---|
| **动作级** | `E1·R1` | 单动作完成 / 查看动作历史 | 动作质量（火柴人+AI 点评）、本次 PB、该动作的进步曲线 | P1 |
| **课程级** ★ | `E2·R1` | 练完一节课 | 全局总结、肌群覆盖、动作列表、本次 vs 上次 | **P0** |
| **计划级** | `E3·R2` | 完成一个 4/8 周计划 | **阶段性成长**：起点 vs 终点、坚持度、能力变化、体适能位移 | P1 |
| **周期级** | `E0·R2` | 周 / 月 / 年结束 | 时间维度累计与趋势、streak、习惯养成 | P1 |

> 四个粒度共用同一套原子与模板机制，差别只在**时间跨度**和**洞察类型**：粒度越大，洞察越偏"成长与归因"；粒度越小，洞察越偏"质量与即时反馈"。

### 2.7 洞察引擎：真正的 wow 来源 ★

**判断**：竞品都能给数据（时长、卡路里、容量）。数据回答"我做了什么"，**洞察回答"这意味着什么"**。用户不会分享一堆数字，但会分享一个让他惊讶或自豪的判断——这是分享动机的核心来源之一。

#### 2.7.1 洞察的三个层次

| 层次 | 定义 | 例子 | 谁能做到 |
|---|---|---|---|
| **L1 陈述** | 数据本身，零洞察 | "你练了 42 分钟，消耗 386 千卡" | 所有 App |
| **L2 比较** | 有参照系 | "比上次多举了 12%"、"超过 88% 的同课学员" | 多数 App |
| **L3 判断** ★ | 有因果、有建议 | "你的卧推进步来自组数 +2 而非重量——下次可以试着加到 65kg" | **我们的差异化** |

> 竞品停在 L1~L2，我们的 AI 识别 + 结构化数据（模式/肌群/器械三个分类实体）让 L3 成为可能。**L3 才是 wow。**

#### 2.7.2 六类洞察（Insight Types）

| 类型 | 逻辑 | 例子 | 数据依赖 | 冷启动 |
|---|---|---|---|---|
| **① 对比型** Comparison | 与参照系比 | 本次 vs 上次 / vs PB / vs 同课人 | ≥2 次记录（或榜单） | 第 2 次可用 |
| **② 发现型** Discovery | 揭示用户不知道的模式 | "你 78% 的训练容量集中在推类" | 维度聚合（E5/E6/E7） | 第 5 次起 |
| **③ 归因型** Attribution | 拆解为什么变好/变差 | "进步来自组数 +2，重量持平" | 多变量分解（容量=重量×次数×组数） | 第 5 次起 |
| **④ 预测型** Projection | 按趋势外推 | "按当前节奏，4 周后可破 70kg" | 趋势拟合（≥4 个点） | 第 8 次起 |
| **⑤ 异常型** Anomaly | 全量排序中的极值 | "今年最强的一次训练"、"首次连续 3 周不缺勤" | 全量排序 | 第 10 次起 |
| **⑥ 具象型** Analogy | 抽象数字 → 可感知类比 | "1,800kg ≈ 举起一辆车" | 类比素材库 | **第 1 次即可用** |

#### 2.7.3 分享价值公式与"双面报告"规则 ★

**分享价值 = 意外性 × 正面性 × 可炫耀性**

- **意外性**：用户已知的信息没有分享价值（"我练了胸"他自己知道）；
- **正面性**：负面洞察不会被分享（"你三周没练背了"——自己看有用，分享不会）；
- **可炫耀性**：能体现努力、天赋或坚持。

由此得出一条重要产品决策——**双面报告**：

| | App 内报告 | 分享出去的报告 |
|---|---|---|
| 角色 | **教练**：该说的都说 | **战报**：只带能炫的 |
| 洞察范围 | 全部六类，含负面与改进建议 | 仅正面洞察 + 中性事实 |
| 数量 | 完整列出 | **只突出 1~3 条**（按分享价值分排序） |

> 与"一张图一个主角"同源：洞察也要**被选出来**，不是全堆上去。堆满 8 条洞察 = 没有洞察。

#### 2.7.4 洞察可用性阶梯（冷启动设计）

新用户没有历史，洞察引擎会"哑火"——必须提前设计降级路径：

| 用户阶段 | 可用洞察 | 报告主打什么 |
|---|---|---|
| 第 1 次 | 仅⑥具象型 + L1 陈述 | 具象类比 + 火柴人 AI 点评（**不依赖历史**，这是我们的优势） |
| 第 2~4 次 | +①对比型 | "比上次更好"的即时正反馈 |
| 第 5~9 次 | +②发现型 +③归因型 | 开始"懂你"：模式分布、进步归因 |
| 第 10 次起 | 全部六类 | 完整教练体验：预测、里程碑、异常提示 |

> **冷启动的关键**：火柴人 AI 点评（C1/C2）和具象类比（A4）**第一次训练就能给出 wow**，不依赖任何历史数据——这是我们相对竞品的结构性优势，应该在新用户首份报告里重点用。

### 2.9 媒体资产族：分享体的"第二种物质" ✅ 新增 2026-08-21 ★

此前把影像当作"依附训练记录的可选原子"（D1/D2）——**低估了**。训练影像是独立的一族，而且在社交平台（小红书/IG/TikTok 都是媒体优先）**传播力最强**。

#### 2.9.1 两种物质模型

任何分享体都由两种"物质"构成，多数分享是两者混合，也存在纯媒体的分享：

| | 数据物质 Data matter | 媒体物质 Media matter |
|---|---|---|
| 来源 | 结构化数据 → **渲染**（我们画出来） | 摄像头 → **捕获** → AI **处理** |
| 原子类 | A 数据 · B 结构 · C AI 分析 | **M 媒体资产** |
| 分享潜台词 | "看我达成了什么" | "看我这个人 / 这画面很酷" |
| 平台契合 | 需要设计成图才好看 | **平台原生内容，天然高传播** |

#### 2.9.2 M 类媒体资产目录

| 编码 | 资产 | 说明 | 分享意愿 | 差异化 |
|---|---|---|---|---|
| **M1** | 原始训练视频 | 整段录制，主要用于自己复盘 | 低（太长太平） | 通用 |
| **M2** | **高光视频片段** | AI 自动剪出的 5~15s 精彩片段（最大重量那组/形态最标准的一次/力竭前最后一次） | **高** | ✅ 自动选材依赖姿态识别 |
| **M3** | 高光照片 | 从视频 AI 抽帧的最佳静帧（发力峰值、动作顶点） | 高 | ✅ 同上 |
| **M4** | **漫画 / 风格化影像** ★ | AI 把训练影像转成漫画、赛博、复古海报、像素、水墨等风格 | **最高** | ✅ **最 AI-native 的传播形态** |
| **M5** | 姿态叠加影像 | 骨架/火柴人叠加在真人影像上（C1 的动态真人版） | 中高 | ✅ **独有** |
| **M6** | 前后对比影像 | 计划级：8 周前后的体态或动作对比 | 高（成长叙事） | 🟡 依赖计划体系 |
| D1 | 用户自拍 / 氛围图 | 用户主动上传的照片（非训练捕获），保留在 D 类 | 中 | 通用 |

> **迁移说明**：原 `D2 高光视频` 并入 `M2`，D 类此后只保留 D1 氛围图与 D3 文案。

#### 2.9.3 媒体处理管线（我们的结构性优势）

```
原始录制 → AI 姿态识别（已有能力）→ 自动选材 → 风格化 → 叠层 → 成片
                    ↑                    ↑           ↑        ↑
              我们已经在做           知道"哪一秒        风格模板   数据角标
                                     最精彩"                  （重量/PB）
```

**为什么竞品做不了自动选材**：他们要么没有视频，要么只能让用户手动剪。我们因为在做姿态识别，**天然知道哪一帧最精彩**。可用的选材信号（全部来自已有数据）：

- 最大重量那一组的那一次 · 动作评分最高的一次（形态最标准）
- 力竭前的最后一次（最有戏剧张力）· PB 达成的那一次 · 完成瞬间/结束姿态

#### 2.9.4 漫画照片（M4）为什么值得单独立项 ★

1. **解决"不好意思晒自己"**——风格化是一层心理滤镜，显著降低出镜门槛（健身房自拍尴尬、素颜、身材焦虑）；
2. **平台算法友好**——小红书/IG 对风格化视觉的点击率天然更高；
3. **话题自带传播**——"我的训练变成了漫画"本身就是可讨论的内容，不需要解释；
4. **隐私友好**——风格化天然降低面部可识别度，副作用正好是优点。

**风格档位建议**（每种是一个模板而非随机生成）：漫画/manga（力量感线条）· 赛博霓虹 · 复古运动海报 · 像素 · 水墨。建议先做 2~3 种做透，而不是给 10 种都很平庸。

#### 2.9.5 媒体隐私规则（比数据更敏感）

| 风险 | 默认处理 |
|---|---|
| **本人面部** | 提供一键风格化/打码；M4 风格化天然弱化 |
| **背景环境** | 家中背景可能泄露住址/生活信息 → 提供背景虚化或替换 |
| **画面中的他人** | 健身房路人 → **自动检测并模糊**（不可依赖用户自觉） |
| **原始素材** | 优先端上处理；需上云时明确告知并限定留存期 |

> 与 2.8 三档隐私分级一致：媒体属于**谨慎级**——默认不自动分享，必须用户主动选择。

### 2.8 健康域扩展预留（大一统健康数据中心视角）🔮

**假设**：未来 BodyPark 是大一统的健康运动数据中心（对标 Apple Health / Google Health Connect）。检验结论：**架构不需要改**——新域接入 = 矩阵加实体行 + 原子目录加 H 系原子，关系态轴（R0~R3）、表现形式、载体、分发链路全部复用。

**预留实体（E8~E11，可分享优先域）**：

| 实体 ＼ 关系态 | R0 内容态 | R1 实例态 | R2 聚合态 | R3 衍生态 |
|---|---|---|---|---|
| **E8 身体指标** | 指标科普卡 | 单次称重（弱） | **体重/体脂趋势**、变化量 | 减重里程碑徽章 |
| **E9 饮食/膳食** | 食物/食谱卡 | **一餐打卡**（照片+宏量） | 营养周报、热量收支 | 连续打卡 streak 徽章 |
| **E10 运动会话**（跑步/骑行等非课程运动） | 运动方式科普卡 | **单次跑步**（路线+配速+心率） | 月跑量、配速趋势 | 累计里程徽章（"百公里俱乐部"） |
| **E11 睡眠** | 睡眠科普卡 | **昨晚睡眠**（结构图+时长） | 睡眠周报、规律性 | 早睡/规律徽章 |

**三档隐私分级**（新增的架构规则，健康域必备）：
1. **默认可分享**：训练、活动、营养、睡眠——正常进入分享流程；
2. **谨慎级**：身体绝对值、心肺指标——默认隐藏或只显趋势，需用户主动勾选才外显；
3. **禁止级**：医疗、周期——数据中心收录但**永不进入分享模块**（分享源不出现分享按钮）。

> 协同效应：大一统数据中心让 **Pro 数据导出（给 Agent）** 的叙事更完整——"所有能吐数据的 App"里，我们成为聚合方而非被聚合方。

## 3. 第②层 · 内容原子目录（Atom Catalog）★核心

分享内容的**有限积木**。会议已验证 5 个高意愿通用原子 + 3 个自有差异化原子（见附图《原子模块表》）。这里补全并分组，附**所需数据字段**与**空状态策略**（会议强调："别再出现一堆 0 / — / 空，排版上要把它补满"）。

### 3.0 原子的多态性：一个模板，多种数据绑定 ★设计共性模块的钥匙

同一个原子在不同关系态（R0~R3）下**版式模板复用，只换数据绑定**。这就是"针对共性模块设计模板"的落点——每个原子只设计一次，声明它支持哪几种绑定：

| 原子 | R0 内容态绑定 | R1 实例态绑定 | R2 聚合态绑定 |
|---|---|---|---|
| **肌肉热力图** | 解剖态：该动作的主动肌/协同肌（primary/secondary） | 本次练到的肌群 × 强度着色 | 本周期肌群覆盖热度（哪块常练/欠练） |

| **历史对比** | — | 本次 vs 上次 / vs PB | 趋势曲线 |

> 开发含义：原子组件的 props = `template + bindingMode + data`。设计含义：设计师按原子出模板，每个模板标注适配的绑定态与空状态规则，而不是按页面出图。

### 3.1 数据类原子（Data）
| 原子 | 说明 | 所需数据字段 | 空状态策略 | 差异化 |
|---|---|---|---|---|
| **训练总结指标** | 时长/容量/卡路里/心率/组次 | duration, volume, calories, avgHR/maxHR, reps, sets | 缺项则排版重排为"满格"，不留空宫格 | 通用 |

### 6.0 表现形式词汇表（Format Vocabulary）

| 表现形式 | 说明 | 典型原子 |
|---|---|---|
| **数字 Number** | 大数字、宫格指标、计数 | A1 A2 |
| **图表 Chart** | 趋势线、对比条、雷达、热力图着色 | A3 C3 B2 |
| **照片 Photo** | 氛围图、自拍、封面 | D1 B3 B4 |
| **视频 Video** | 高光片段、动态回放 | D2 |
| **徽章 Badge** | 勋章、评级字母、里程碑标识 | C4 E4·R3 |
| **可视化指标 Visual Metric** | 进度环、六边形 PPS、莲花、打卡点阵 | C4 A2 |
| **数字人 Digital Human** | 火柴人姿态、未来 3D avatar/数字分身 | C1 |

> 设计含义：模板 = 原子组合 × 每个原子选定的表现形式。比如同一个 A2 周期统计，可渲染成"数字"（大数字 5/7），也可渲染成"可视化指标"（打卡点阵）。这张词汇表也是设计师做风格探索时的自由度边界。

### 6.1 自由度三级模型（渐进式披露）✅ 已决策 2026-07-16

主体由分享源定死（见 2.0），主体**内**的组合自由度分三级，"尽量保持简单"：

| 级别 | 面向 | 交互 | 决策成本 |
|---|---|---|---|
| **L1 · 默认模板** | 全部用户 | 发起分享即出图，零配置 | 0 步 |
| **L2 · 精选模板** | 普通用户 | 每主体预设 2~4 个常见模板（不同原子组合+版式），横滑切换 | 1 步 |
| **L3 · 自由组合** | 高阶用户 | 菜单式勾选原子（参考"练就/训鸡"做法，勾选即显示），入口收敛在模板列表末位"自定义" | N 步，自愿进入 |

> 逻辑：L1/L2 是我们替用户做的**强意见**（穷举常见诉求做成模板）；L3 是给高阶用户的**逃生口**，避免霸道又不让菜单复杂度污染主流程。模板本质 = 一组预设的"原子勾选状态 + 版式"，所以 L2 与 L3 底层同构，代码只有一套。

### 6.2 P0 · 课后报告（E2·R1）的 L2 精选模板定义（低保真任务书）

四个模板 = 四种预设的原子组合。T1 即 L1 默认；低保真原型见 `04-设计-原子与报告.html`。

| 模板 | 定位 | 版式 | 原子组合（按序堆叠） |
|---|---|---|---|
| **T1 战报短图**（默认） | 一键出图、最易传播 | 短图（固定比例） | A1 + B2(R1) + G1 |
| **T2 完整长图** | 完整战报、有点有面 | 长图 | A1 + B2(R1) + B1(R1) + A3 + G1 |
| **T3 AI 特色版** | 独有差异化、火柴人 | 短图/长图 | C1 + C2 + A1(精简) + G1 |
| **T4 极简晒图** | 情绪价值、氛围感 | 短图 | D1(全幅) + A1(一个大数字) + A4 + G1 |

规则：G1 在图片载体必带（引流兜底）；A3/A4 无达标数据自动隐藏并重排；D1 无上传用系统配图兜底。
- **三种版式**：
  - **短图（卡片）**：固定长宽比，信息量受高度约束，默认输出、最易传播（"机器摆那拍张图直接发"式的低门槛）。
  - **长图**：想多长多长，承载多原子叠加，适合完整战报。
  - **卡片**：单动作卡/课程卡/成就卡，独立可分享的最小单元。
- **两个增强引擎**（把枯燥数据变有趣）：
  - **具象化引擎**：指标 → 类比（1800kg=举起一辆车、kcal=消耗几个汉堡）。
  - **对比引擎**：本次 → vs 上次 / PB / 本月第几次，体现"App 有历史趋势与洞察能力"。

## 7. 第④层 · 载体与格式（Carrier）✅ 扩展 2026-07-17

同一份分享体数据，可以用**五大载体族**输出。载体与前三层（分享体/原子/模板）完全解耦——换载体不换内容。

### 7.1 五大载体族

| 族 | 载体 | 面向 | 核心优势 | 适用场景 |
|---|---|---|---|---|
| **① 图像 Image** | 短图 / 长图 / 卡片（PNG） | 人 · 社交 | 制作简单、全平台适配、零门槛 | 朋友圈、小红书、IG 的即时晒图 |
| **② 视频 Video** 🆕 | 竖版短视频（MP4） | 人 · 社交 | **平台原生内容、算法权重最高**；有声音、有节奏、有叙事 | Reels / TikTok / 视频号 / Story；M 类媒体资产的主要出口 |
| **③ 交互 Interactive** | **H5 可交互链接**（公域页） | 人 · 深度 | 可交互、可下钻、自带 App 引流入口、内容可更新 | 需要引导转化、内容太多图装不下 |
| **④ 数据 Data** 🆕 | **Markdown · CSV · JSON** | **AI / Agent** | 结构化、可被机器解析、可喂给用户自己的 agent | 极客用户的个人健康数据中枢（Pro） |
| **⑤ 文档 Document** 🆕 | **PDF 专业报告** | 人 · 专业 | 打印级排版、图表完整、像"体检报告" | 给教练/医生/自己存档的专业留痕 |
| 附 · 入口 | 二维码 | 人 · 线下 | 成本低、适配多端 | 私域社群、线下器械旁扫码 |

> 二维码不是独立载体，而是**指向 H5 的入口形态**（可嵌在图像里，也可独立出现）。

### 7.2 为什么在 AI native 时代要做数据类载体

会议里提到的真实用户画像："一个哥们身上戴着 Loki、Whoop 一堆设备，所有能吐数据的 App 他都用，全喂给自己的 agent 做长寿分析。"

- 这类用户不需要"好看的图"，需要的是**可被机器读取的结构化数据**；
- 我们做数据导出，意味着在他的健康数据中枢里**我们是数据源而不是数据孤岛**；
- 结合 2.6 的大一统健康中心假设，我们甚至可以成为**聚合方**——他把别家数据导入我们，再从我们导出给 agent。
- 商业上：作为 **Pro 高阶功能**，普通用户无感，专业用户愿意为此付费。

### 7.3 数据类载体规格（Data Carrier Spec）

| 格式 | 结构 | 典型用途 | 分享体支持 |
|---|---|---|---|
| **Markdown** | 带标题层级的可读报告 + 表格；YAML front matter 承载元数据 | 直接粘贴进 ChatGPT / Claude / Notion；agent 可读可读人也可读 | 全部格子 |
| **CSV** | 扁平表：一行一组（set）或一行一次训练 | Excel / Google Sheets / 数据分析脚本 | R1 R2（时序数据） |
| **JSON** | 完整对象树，含 schema 版本号 | 开发者、自建 agent 的程序化接入 | 全部格子 |

**Markdown 导出示例结构**（课后报告 E2·R1）：

```markdown
---
source: BodyPark Atom
type: workout_session
date: 2026-07-17
schema: v1
---
# 上肢推力 · 杠铃与哑铃

| 指标 | 数值 |
|---|---|
| 训练时长 | 42:18 |
| 总容量 | 1,800 kg |
| 消耗 | 386 kcal |
| 平均心率 | 148 bpm |

## 动作明细
| 动作 | 组×次 | 重量 | 容量 |
|---|---|---|---|
| 杠铃卧推 | 4×12 | 60kg | 2,880kg |
...

## 肌群参与
胸(主) 62% · 三角肌前束 21% · 肱三头肌 17%

## AI 分析
- 深度到位，髋膝同步良好
- 起身时膝盖轻微内扣，注意外展发力
```

**导出规则**：① 时间戳统一 ISO 8601；② 单位随用户设置（kg/lb）并在 front matter 声明；③ 含 `schema` 版本号便于向后兼容；④ 隐私分级同 2.8——禁止级数据永不进入导出。

### 7.4 交互类载体规格（H5）

- **公域可访问**：无需登录、无需下载 App 即可查看（这是引流的前提）。
- **比图片多的三件事**：① 可下钻（点动作看详情/看视频）② 可播放（火柴人动效、高光视频）③ 可更新（数据修正后链接内容同步）。
- **必带 G2 App 下载入口**：deeplink 优先，未装落商店。
- **与图片同源**：H5 复用同一份模板 DSL 渲染（M3 里程碑），不做两套设计。

### 7.4b 视频载体规格（Video）🆕

- **默认竖版 9:16**，时长 **5~15 秒**（Reels/TikTok 的完播率甜点区）；长版 30~60s 作为可选档。
- **前 3 秒定生死**：开场必须直接给最精彩的画面（AI 选材的峰值帧），数据叠层后置，不做片头 logo。
- **叠层 = 静态原子的动态版**：重量/PB/名次角标复用同一套 token 与字阶，出现在安全区内；grid-spec 的安全区规则同样适用。
- **必须无声可看**：平台默认静音播放 → 关键信息必须是画面上的字，不能只靠音频。
- **收尾 1~2 秒**品牌帧 + 二维码（对应图像载体的 G1 水印位）。
- **导出**：H.264 / 1080×1920 / 30fps；端上合成优先，避免上传原始素材。

|---|:--:|:--:|:--:|:--:|:--:|

### 13.3 工程（可复用架构模块：ShareKit）

**目标**：全 App 唯一的分享模块，"新场景 = 配置，不是开发"。

**四层管线**（与五层模型对应，①②合并为数据面）：

```
DataProvider 层   每实体一个 Provider，实现统一接口：
                  provide(entityId, relationState) -> AtomData[]
                  · 原子声明 requiredFields + emptyPolicy(hide/fallback/rearrange)
                  · 隐私分级在此层强制：禁止级实体不注册，分享入口不出现
        ↓
Composition 层    模板注册表（JSON/服务端可下发）：
                  Template = { subjectCell, atoms[{code, format, options}], layout }
                  · L1/L2/L3 同构：模板 = 预设勾选态；L3 = 用户改勾选态
                  · 组合器执行"满格"规则：缺数据原子自动隐藏并重排
        ↓
Render 层         原子组件库（App 原生 + H5 同一套模板 DSL）：
                  render(AtomSpec, AtomData, theme) -> View
                  · 短图=固定画板 / 长图=纵向拼接 / 卡片=独立画板
                  · 服务端出图兜底（分享给未装 App 的 H5 场景）
        ↓
Carrier 层        导出与分发：
                  image(尺寸预设+水印+QR注入) / H5(公域路由+deeplink) / QR
                  · 平台尺寸档位表与 Composition 解耦
                  · 埋点在此层统一打
```

**核心数据契约**（伪码）：

```ts
type RelationState = 'R0'|'R1'|'R2'|'R3'
interface ShareSubject { entity: EntityType; entityId: string; state: RelationState }
interface AtomSpec { code: AtomCode; format: FormatType; binding: RelationState }
interface AtomProvider {
  supports: AtomCode[]
  provide(subject: ShareSubject): Promise<AtomData | Empty>  // Empty 携带 emptyPolicy
}
interface Template { id: string; cell: string /*E2R1*/; atoms: AtomSpec[]; layout: 'short'|'long'|'card' }
```

**里程碑**：
- **M1**（对应 Phase 2）：ShareKit 内核 + E2·R1 Provider + T1 模板 + 图片载体。
- **M2**：模板注册表服务端化 + L3 勾选 + T2~T4。
- **M3**（对应 Phase 4）：公域 H5 渲染复用模板 DSL + QR/链接载体 + 回流归因。
- **M4**：新实体接入手册化——写一个 Provider + 配一份模板 JSON 即上线（E5/E6/E7 用此路径验证）。

**接入新分享场景的标准流程**（M4 后）：定义实体格子 → 实现 Provider → 配模板 JSON → 在分享源挂入口。零 UI 开发（复用原子组件），零分发开发（复用载体层）。

## 14. 邀请分享与归因（Referral & Attribution）✅ 新增 2026-09-03 ★

> 可视化版：`05-推荐-邀请分享与归因.html`（含可交互链路模拟器）

**定位：不是新模块，是分享模块上的一层薄挂载。** 邀请是内容的副产品，不是内容本身——所以它不新增载体族、不新增自由度层级，只在既有五层模型里各加一点点。

### 14.1 三条基础判断

| # | 判断 | 为什么 |
|---|---|---|
| **A** | **目标落到电商购买页（优先硬件），而不是应用商店** | 跳商店的链路里，iOS 没有官方按人延迟深链、微信屏蔽 `itms-apps`、国内安卓没有统一商店与 Install Referrer——只能做概率匹配。落到购买页后，归因点从"安装时刻"移到"**下单时刻**"：订单一定有号、一定能带码、一定进账本。**整条阶梯每层都是确定性的，没有概率层。** |
| **B** | **H5 落地页是唯一的变化点** | 分享物（图片、短链）全球是同一份；地区/环境/目标差异全部由落地页在运行时吸收。App 端和 Atom 设备端**不需要写任何地区逻辑**——它们只渲染一个 token。国际化 = 多配几份 Profile，不是多做几套分享 UI。 |
| **C** | **一个码，两个时刻** | 优惠码在**结算时是折扣**（促成交，被邀请人的钩子），在**首次激活 Atom 时是凭证**（做归因，邀请人的奖励依据）。同一个码复用两次——所以即使在天猫/京东这类归因黑洞里成交，激活那一刻也能把关系补回来。 |

### 14.2 归因五级阶梯（按序命中即停，全部确定性）

| 层 | 归因点 | 触发时机 | 确定性 | 覆盖 |
|---|---|---|---|---|
| **L0** | 自有商城订单带 token（`order.referral_token`） | 落地页 → 自有商城下单 | **确定 100%** | 官方商城 / 微信小程序商城 / 海外独立站。唯一完全可控的一层，也是把用户往自有渠道推的最强理由 |
| **L1** | 专属优惠码在结算时被使用 | 任意电商结算页 | 需用户动作 | 用了就 100% 准，问题是漏斗漏。天猫/京东对自定义券码有规则限制，需与运营确认可用形态 |
| **L2** | 平台联盟追踪链接（淘宝客 / 京东联盟 / Amazon Attribution） | 落地页 → 第三方平台 | 平台口径 | 需入驻、结算走平台、**回传粒度到渠道而非到人**。建议只做渠道级统计，**不作为发奖依据** |
| **L3** ★ | **首次激活 Atom 时填邀请码**（`activation.referral_code`） | 硬件开箱 → App 配网激活 | **确定 100%** | **与"在哪买的"完全无关**——天猫、京东、线下、别人转送全兜住。激活本来就必须走我们的 App。**电商优先方案里最重要、且唯一覆盖全渠道的一层** |
| **L4** | App 内自助补填 | 激活后 7 天内 | 需用户动作 | "忘填邀请码？"入口，限时限次；同时给邀请人"提醒 TA 填码"的动作 |
| ~~—~~ | ~~安装归因 / IDFA 概率匹配~~ | — | **已移除** | 电商优先下不需要。App 下载作为次要目标时，Android 用 Play Install Referrer，iOS 走 L3/L4，**不引入任何第三方归因 SDK** |

> **设计含义**：因为 L3 覆盖全渠道且 100% 确定，不必强求 L0/L1 的漏斗完美。**L0/L1 优化成交转化，L3 保证关系记账——两件事分开算 KPI，不要混。**

### 14.2b 简化口径 ✅ 已决策 2026-09-03

> 归因不必做到上面阶梯的全部。**业务侧只需要一个数：通过分享带来的订单数**——订单带 token（L0）或激活时填码（L3）两条来源相加即是，不需要联盟链接、不需要安装归因 SDK。L1/L2/L4 保留为参考，P0 不做。

>

### 14.2c 邀请页三条约束 ✅ 已决策 2026-09-03

1. **页面只有一个 CTA**（"邀请好友"）。形式（图 / 链接）与去处（微信 / 相册 / iMessage / 更多…）是同一个决定的两半，放在 CTA 拉起的**同一张面板**里一次选完；每个去处都是终点。邀请码留在页面上但**不做成按钮**，三格数据和"规则"是导航不是 CTA。
2. **分中国版 / 国际版两个版本**。版本决定**做什么**：好友利益（¥500 / $70）、权益阶梯（配件券 ¥199 / $29 credit）、成交场（小程序商城 / bodypark.com）、分享去处、默认形式（CN 图片在前 / GLOBAL 链接在前）、规则文案。版本判定用 App Store 区 / 账号归属地，不用 IP。
3. **多语言独立于版本**。语言决定**说什么**：所有文案走字符串表，金额/天数/昵称作为参数注入；昵称脱敏与日期格式按语言（`Lin**` / `Lin W.`，`09-01` / `Sep 1`）。版本配置里的字符串自身带语言键（`tier3: {zh, en}`），所以**版本 = 一份带语言键的配置，语言 = 选哪个键；加一门语言 = 加一列**。设计稿按英文最长版定容器高度（英文比中文长 30%~50%）。

### 14.3 两种分享形式（且只有两种）

邀请码**不是第三种形式**——它印在图片上、显示在落地页上，是这两种形式内部的一个字段。

**形式一 · 图片（带二维码）**，三个变体：

| 变体 | 来源 | 说明 |
|---|---|---|
| **A 内容图挂载** ★主路径 | 任意 27 个模板 | G1 水印二维码里本来就该带 token。用户在分享训练成果，邀请是免费搭车的副产品——**量最大、零额外动作、零新增设计** |
| **B 专用邀请卡** | "邀请好友"入口 | 新模板 **T28**，3:4 竖版。G3 身份条 + 产品图 + 价格钩子 + G4 明文码 + G1 大二维码 |
| **C 设备屏版** | Atom 设备屏 | 1:1 超大二维码。**设备端图片是唯一可能的形式**——没有浏览器、没有分享面板，只能把码打到屏上让朋友当场扫。这条硬约束单独就足以让图片形式必须存在 |

**形式二 · 直接 URL（H5 落地页）**：短链 `bp.fit/i/7K2A`。落地页是整个方案的**路由器**，必须做六件事：① 认人（token → 邀请人身份 + 训练凭证，社交证明）② 认环境（微信内 / 系统浏览器 / 桌面）③ 认地区（**用 App Store 区 / 店铺归属判定，不要用 IP**）④ 透传 token 给下一跳 ⑤ 始终显示明文码 ⑥ 配 OG / 微信 JS-SDK 卡片元数据（同一个 URL 的渠道渲染，不算第三种形式）。

| 端 | 图片（带二维码） | 直接 URL |
|---|---|---|
| **手机 App** | ✅ 存图 / 朋友圈 / 群 | ✅ 复制 / 微信 / iMessage |
| **Atom 设备** | ✅ 屏幕直出二维码 | ✗ 无分享能力（短链以明文供手输，是图片的降级，不是独立形式） |

### 14.4 Token 与链接结构

```
短链    https://bp.fit/i/7K2A?s=post&c=wx
明文码  ALEX-7K2A
二维码  编码同一条短链
```

- `7K2A` = 邀请人 token，永久绑定，**唯一被解析的部分**。Base32 去歧义字母表（无 `0/O/1/I/L`），4~6 位起步。
- `ALEX-` 前缀纯装饰，便于人念人记；服务端只取后缀，改昵称不影响归因。
- `s`（场景，哪个分享入口生成）、`c`（渠道）**仅用于分析，永不参与归因**。

> **为什么参数必须可丢**：图片会被截图转发、二维码会被翻拍、短链会被手抄。把归因押在 token 上、分析押在参数上，意味着一张图转发十手之后归因依然正确，只是渠道标签失真——可接受。推论：**不做一次性链接、不做有效期链接**（活动券除外），邀请关系是长期资产。

### 14.5 地区 Profile（一个内核 + 可插拔配置）

内核（token 身份、归因账本、奖励引擎、降级链抽象）全球唯一。Profile 注入五样：成交场、落地页形态、归因优先级、奖励形态、合规文案。**新增一个地区 = 加一份配置，不是加一套代码。**

| Profile | 落地页主 CTA | 成交场 | 归因优先级 | 分享通道侧重 |
|---|---|---|---|---|
| **CN** | 买 Atom（小程序商城优先） | 微信小程序商城 >> 天猫/京东 > 线下 | L0（小程序 openid + 订单 token）→ L1 优惠码 → L3 激活回填 | **图片为主**：朋友圈/群图片传播强于链接 |
| **GLOBAL** | Buy Atom（自有独立站） | 自有 Shopify 站 > Amazon | L0（`?ref=` → cart attribute → order）→ L1 coupon → L3 激活回填 | **链接为主**：iMessage/WhatsApp/IG 对链接友好 |
| **APP_ONLY**（次要） | 下载 App | App Store / Google Play | Android: Play Install Referrer（确定性）；iOS: 无官方按人延迟深链 → 直接 L4 | 仅当访客已有硬件或明确是 App 用户时启用 |

**三条 CN 特殊规则**：① 微信内不出现任何应用商店跳转（电商优先已天然满足）；② 小程序商城如能上，它同时解决成交与归因两件事，**应作为国内主路而非降级路**（openid 归因近 100%，微信内传播衰减远小于 H5）；③ 安卓渠道包只能做到**渠道级**、做不到人级归因，不要指望它替代 L3。

### 14.6 奖励与风控

- **被邀请人**：硬件立减。钩子必须在成交前可见，否则不构成购买理由。
- **邀请人**：优先给**权益**而非现金（会员时长、配件券、限定内容、积分）——国内现金返利涉及税务与资质。可做阶梯（邀 1/3/5 人递增），但阶梯要在邀请卡上说清楚，否则不产生持续动机。
- **结算时点**：邀请人奖励在**确认收货 + 完成激活**之后发放，不在下单时发（硬件退货率不为零，提前发奖是套利入口）。账本三态：`attributed` → `qualified` → `settled`，三态分离才对得清账。
- **反薅**：同设备指纹 / 同支付账号 / 同收货地址高频 → 人工审核；邀请人需**已激活设备且有真实训练记录**才有发奖资格（门槛放在邀请人侧比放在被邀请人侧更不伤转化）；异常速率**挂起而非拒绝**，避免误伤真实 KOC。

### 14.7 接入现有架构

| 层 | 改动 | 说明 |
|---|---|---|
| **① 分享体** | 新增 `E12 · 推荐邀请`（仅 R1） | 只为让邀请卡在矩阵里有位置，不参与 R0/R2/R3 |
| **② 原子** | G 族 2 → 4 个 | `G1` 注入 token（改造，所有模板受益）· `G2` App下载入口 → **购买入口** · `G3` 邀请人身份条 🆕 · `G4` 明文码条 🆕（见 3.5） |
| **③ 组装** | 新增 `T28 邀请卡`（3:4 手机版 / 1:1 设备版） | 模板注册表加两条 JSON；其余 27 个模板**不改结构**，只是 G1 里的二维码内容变了 |
| **④ 载体** | **不新增** | 只用既有的 ①图片 PNG 与 ③H5，与"两种形式"的约束一致 |

### 14.8 待拍板（六个）

| # | 谁定 | 问题 | 影响 |
|---|---|---|---|
| 1 | 电商/运营 | **小程序商城这一路走不走得通？** | 国内方案强弱几乎全押在这里。能上 = L0 直通、归因近 100%、传播衰减最小；上不了则退化为"优惠码 + 激活回填"双腿走路 |

| 6 | 硬件 | 设备屏能不能显示**动态**二维码？ | 决定设备端邀请是"每台固定一张图"还是"按登录用户生成"。若只能静态，设备端邀请无法归因到人，需降级为渠道码 |
